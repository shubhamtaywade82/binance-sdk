# Is `binance-sdk` Fully Contract-First? — Architecture Audit

> Scope: `shubhamtaywade82/binance-sdk` @ `main` (commit `556a629`).
> Compared against the strict definition of "contract-first": a single
> machine-readable contract is the source of truth, and the typed
> client surface, validators, route handlers, tests, and docs are all
> **generated** from it — never hand-written alongside it.

---

## TL;DR

**No, the SDK is not fully contract-first today.** It sits on a
**registry-first hybrid**: the *endpoint inventory* (path, method, auth,
weight, implementer) is a hand-curated TypeScript registry that drives a
generated `endpoint-catalog.json`, but the *request/response schemas*,
the *resource classes*, and the *type definitions* are all
hand-written alongside the registry. The repo's own comments admit
this is a stepping stone toward a fully generated contract layer
(OpenAPI → typed clients).

Concretely:

| Layer                       | Contract-first?       | Source of truth                              |
| --------------------------- | --------------------- | -------------------------------------------- |
| Endpoint inventory          | ✅ Yes (registry)     | `src/registry/*.endpoints.ts`                |
| Generated catalog JSON      | ✅ Yes (derived)      | `contracts/*.json` (regenerated by script)   |
| Catalog drift CI check      | ✅ Yes                | `test/contracts/catalog.test.ts`             |
| Endpoint-map docs / `llms.txt` | ✅ Yes (generated) | `scripts/generate-endpoint-map.ts`           |
| Request/response schemas    | ❌ No (hand-written)  | `src/types/*.types.ts` (Zod, ~2 100 LOC)     |
| Resource classes (HTTP calls) | ❌ No (hand-written) | `src/resources/*.ts` (~10 files)              |
| Method signatures / DTOs    | ❌ No (hand-written)  | inline in resource files                      |
| Request-weight declarations | ❌ Partial            | hand-coded `ENDPOINT_WEIGHTS` map in `src/contracts/index.ts` |
| OpenAPI / AsyncAPI spec     | ❌ Does not exist     | —                                            |
| WebSocket stream contracts  | ❌ Partial            | `contracts/websocket-catalog.json` carries connection limits + endpoints, **not** per-stream payload schemas |

The codebase is therefore roughly **60 % of the way to contract-first** —
the inventory half is solid; the schema/method/type half is still
hand-curated.

## What "fully contract-first" would mean for this repo

A fully contract-first binance-sdk would have one machine-readable
**specification** per Binance product family (Spot, USDⓈ-M, COIN-M,
PM, Options, PM Pro, Crypto Loan, Convert SAPI, Algo SAPI, Dual
Investment, Alpha, Copy Trading, C2C) — and the SDK's public surface
would be **derived** from those specs:

```
contracts/openapi/
  spot.yaml
  usdm.yaml
  coinm.yaml
  pm.yaml
  options.yaml
  pm-pro.yaml
  crypto-loan.yaml
  convert-sapi.yaml
  algo-sapi.yaml
  dual-investment.yaml
  alpha.yaml
  copy-trading.yaml
  c2c.yaml

contracts/asyncapi/
  spot-streams.yaml       (market + user-data streams)
  usdm-streams.yaml
  coinm-streams.yaml
  pm-pro-streams.yaml

scripts/
  generate-resources.ts    (OpenAPI  → src/resources/*.ts)
  generate-types.ts       (OpenAPI  → src/types/*.types.ts)
  generate-registry.ts    (OpenAPI  → src/registry/*.endpoints.ts)
  generate-ws-streams.ts  (AsyncAPI → src/ws/*-streams.ts + types)
  generate-contracts.ts   (OpenAPI  → contracts/{endpoint,security}-catalog.json)
  generate-docs.ts        (OpenAPI  → docs/endpoint-map/*.md + llms.txt)
  generate-toolkit.ts     (OpenAPI  → src/tools/*.tools.ts (LLM tool metadata))

src/             ← 100 % generated; no hand-edits allowed (CI greps for `// @generated` headers)
test/resources/  ← generated smoke-test skeletons (hand-edited assertions)
```

The single source of truth is the OpenAPI/AsyncAPI YAML; everything
else is regenerated. Drift is impossible because there is no
hand-written code to drift from.

## Concrete gaps to close

Below, each gap is paired with the specific change that would close
it. Items are ordered by ROI (biggest correctness gain first, polish
last).

### Gap 1 — No machine-readable request/response schema source of truth

**Today**: `src/types/*.types.ts` (2 107 LOC across 13 files) is
hand-written Zod. Adding a new endpoint means: write the Zod schema,
write the resource method, write the registry row, write the test —
four hand-edits that can drift independently.

**Fix**: introduce `contracts/openapi/<product>.yaml` per Binance
product, with full JSON Schema for every request body, query
parameter, and response shape. Generate the Zod schemas from those
specs:

```bash
npm run codegen:types     # openapi → src/types/*.types.ts (Zod)
npm run codegen:resources # openapi → src/resources/*.ts
npm run codegen:registry  # openapi → src/registry/*.endpoints.ts
```

Use [`@asteasolutions/zod-to-openapi`](https://github.com/asteasolutions/zod-to-openapi)
or [`openapi-zod-schemas`](https://github.com/drwpow/openapi-zod-schemas)
to round-trip — either start from Zod and emit OpenAPI, or start from
OpenAPI and emit Zod. The OpenAPI-first direction is preferable
because the spec is the artifact Binance actually publishes.

### Gap 2 — Resource classes are hand-written HTTP calls

**Today**: every method in `src/resources/FuturesAccount.ts`,
`FuturesTrading.ts`, `SpotTrading.ts`, etc. is a one-liner like:

```ts
async balance(): Promise<Balance[]> {
  return BalancesResponseSchema.parse(await this.http.get('/fapi/v2/balance', undefined, 'signed'));
}
```

There are 133 of these. Each one is a place for a typo in the path
(`/fapi/v2/balance` vs `/fapi/v1/balance`), a missed `'signed'`
classification, or a forgotten `.parse()`.

**Fix**: generate the resource classes from OpenAPI. The OpenAPI
spec already declares `operationId`, `method`, `path`, `security`,
and `response` schema — all four pieces of every method body are
derivable. The hand-written code collapses to one template:

```ts
// generated from contracts/openapi/usdm.yaml#operation.balance
// @generated — DO NOT EDIT
async balance(): Promise<Balance[]> {
  return BalancesResponseSchema.parse(
    await this.http.get('/fapi/v2/balance', undefined, 'signed'),
  );
}
```

The `// @generated` header lets CI reject hand-edits via a single grep:

```bash
grep -L "^// @generated" src/resources/*.ts && exit 1  # files without the header
```

### Gap 3 — Weight declarations live in a hand-coded map

**Today**: `src/contracts/index.ts` has an `ENDPOINT_WEIGHTS` map
like `'GET /api/v3/exchangeInfo': 20`. Adding a new endpoint means
remembering to update this map (and Binance occasionally retires or
revises weights, so it rots).

**Fix**: declare weights in OpenAPI via the `x-binance-weight`
vendor extension (or as `x-codeSamples` metadata). Generate the
weights map from the spec; the catalog drift CI test already
catches the case where the generated map doesn't match the
generated catalog.

### Gap 4 — WebSocket stream contracts are connection-only

**Today**: `contracts/websocket-catalog.json` carries
`maxStreamsPerConnection`, `rotationMs`, `staleMs`, the family URLs,
and the platform defaults. It does **not** carry the per-stream
payload schema — the `<symbol>@depth`, `<symbol>@trade`,
`ORDER_TRADE_UPDATE`, `executionReport` shapes all live only in
`src/types/ws.types.ts` and `src/types/userdata.types.ts`.

**Fix**: introduce `contracts/asyncapi/<family>-streams.yaml` per
WS family, with the stream name pattern, payload schema, and
routing rules. Generate the stream-name builders, the parse
helpers, and the type unions from AsyncAPI. The
`UserStreamDispatcher` (merged in PR #40) is already shaped for
this — its `UserDataEvent` union would be generated rather than
hand-curated.

### Gap 5 — Catalog is timestamped but not versioned against a Binance release

**Today**: `contracts/catalog.json` carries `catalogVersion: 1`
and a `generatedAt` timestamp. There is no field saying *"this
catalog was generated against Binance API v3 changelog
2026-10-07"*. When Binance ships a new endpoint, the only way to
know the catalog is stale is to re-run the generator and diff.

**Fix**: add a `binanceApiSnapshot` field to `catalog.json`
carrying the source Binance docs URL + date. The CI drift test
should fail when `binanceApiSnapshot` is older than 30 days
(forcing a refresh cadence).

### Gap 6 — The 253 missing endpoints from the audit have no contract at all

**Today**: the matrix shows 253 missing endpoints across PM,
Options, PM Pro, Crypto Loan, Convert SAPI, Algo SAPI, Dual
Investment, Alpha, Copy Trading, C2C. None of these have an
OpenAPI spec, a registry row, or a resource class. They cannot be
contract-first because they are not anything-first yet.

**Fix**: write `contracts/openapi/<collection>.yaml` per missing
collection **before** writing any TypeScript. The matrix CSV
(merged in PR #41) already enumerates the 253 endpoints with
proposed SDK namespaces and method names — that's the input
checklist for the OpenAPI authoring work. Once the YAML exists,
the resource classes, types, registry rows, and tests are all
generated.

### Gap 7 — No OpenAPI schema validation in CI

**Today**: `test/contracts/catalog.test.ts` checks that
`endpoint-catalog.json` matches the registry. It does **not**
check that the registry matches an external OpenAPI spec (because
none exists).

**Fix**: add a `test/contracts/openapi.test.ts` that runs
`openapi-schema-validator` against every YAML in
`contracts/openapi/`, and an additional check that the generated
resources match the spec's `operationId`s. Red Hat's
[`@redocly/cli`](https://github.com/Redocly/redocly) is the
de-facto lint+validate tool for OpenAPI 3.1.

### Gap 8 — Tool layer is hand-curated metadata

**Today**: `src/tools/spot.tools.ts`, `trading.tools.ts`,
`execution.tools.ts` etc. hand-write JSON-Schema-to-Zod mappings
for the LLM/MCP tool surface. Every new endpoint means a parallel
hand-edit in the tools layer.

**Fix**: generate the tool layer from the same OpenAPI specs.
The OpenAPI `operationId` becomes the tool name; the request
schema becomes the input JSON Schema; the response schema
becomes the tool's output. The `toJsonSchema` / `toOpenAITool` /
`toAnthropicTool` / `toMCPTool` helpers in `src/tools/types.ts`
already shape the surface — they just need to be fed by
generated definitions instead of hand-written ones.

## Roadmap: getting to fully contract-first

This is sequenced for incremental shippability — each phase
leaves the SDK in a working state and lands value independently.

### Phase 1 — Author the OpenAPI specs for the existing 133 endpoints (2-3 weeks)

Don't generate anything yet. Just write
`contracts/openapi/{spot,usdm,coinm,margin,wallet,subaccount}.yaml`
covering the 133 endpoints that already exist in the registry.
Validate against Binance's published docs. Add a CI test that
asserts `ENDPOINT_REGISTRY` matches the OpenAPI `operationId`s
(adding operations to OpenAPI without adding them to the
registry now breaks CI — closes drift in both directions).

**Exit criterion**: every endpoint in `src/registry/*.endpoints.ts`
has a matching `operationId` in `contracts/openapi/*.yaml`, and the
CI test passes.

### Phase 2 — Generate the registry from OpenAPI (1 week)

Replace `src/registry/*.endpoints.ts` with a generated file. The
generator reads the OpenAPI specs and emits the same `Row[]` shape
the registry currently uses by hand. The
`scripts/generate-contract-catalog.ts` and
`scripts/generate-endpoint-map.ts` scripts already read the
registry, so they keep working unchanged.

**Exit criterion**: `src/registry/*.endpoints.ts` carries
`// @generated` headers; `git diff` after deleting a row from
OpenAPI shows it disappear from the registry; CI rejects manual
edits to the registry file.

### Phase 3 — Generate the Zod types from OpenAPI (2 weeks)

Use `openapi-zod-schemas` (or hand-roll a small generator) to emit
`src/types/*.types.ts` from the OpenAPI schemas. The
`BalancesResponseSchema`, `AccountSchema`, `PositionRiskSchema`
etc. all become generated. Resource methods that currently
`.parse()` against these schemas keep working — the schema names
just move from hand-curated to generated.

**Exit criterion**: `src/types/*.types.ts` files all carry
`// @generated` headers; the existing test suite (670 tests) still
passes against generated types; a sample diff shows that adding a
new field to an OpenAPI response schema makes the corresponding
Zod schema's `.parse()` accept it.

### Phase 4 — Generate the resource classes from OpenAPI (2-3 weeks)

The biggest mechanical change. Each `operationId` becomes a
method on the matching resource class (SpotTrading, FuturesAccount,
etc.). The generator emits:

```ts
async <operationId>(params: <OperationId>Request): Promise<<OperationId>Response> {
  return <OperationId>ResponseSchema.parse(
    await this.http.<verb>('<path>', params, '<auth>'),
  );
}
```

Existing resources become thin wrappers — or get fully replaced.
The hand-written `FuturesOps.ts` (compositional helpers like
`sizePosition` and `bracketOrder`) stays hand-written because it
is SDK ergonomics, not protocol surface.

**Exit criterion**: every file in `src/resources/` (except
`FuturesOps.ts` and similar composition helpers) carries
`// @generated`; the existing test suite still passes; a diff
shows that adding a new operationId to OpenAPI makes a new method
appear on the matching resource class without any hand-editing.

### Phase 5 — Author AsyncAPI specs for WS streams (2 weeks)

Write `contracts/asyncapi/{spot,usdm,coinm}-streams.yaml` covering
market streams and user-data streams. Generate the stream-name
builders (`FuturesMarketWS.klines()` etc.), the payload parsers
(`parseWsPayload`), and the typed event unions (`BinanceUserEvent`)
from AsyncAPI.

**Exit criterion**: `src/ws/*-streams.ts` and the WS-payload parts
of `src/types/*.types.ts` carry `// @generated`; the existing WS
test suite (8 test files) still passes; the
`UserStreamDispatcher`'s `UserDataEvent` union is generated from
the AsyncAPI spec rather than hand-curated.

### Phase 6 — Generate the LLM tool layer from OpenAPI (1-2 weeks)

The `src/tools/*.tools.ts` files become generated. The OpenAPI
`operationId` becomes the tool name, the request schema becomes
the tool input, the response becomes the tool output. Hand-curated
tools (the `paper.tools.ts`, `derived.tools.ts`) stay hand-written
because they wrap multiple endpoints with extra ergonomics.

**Exit criterion**: `src/tools/{marketData,account,trading,spot,ws}.tools.ts`
carry `// @generated`; the `createFuturesToolkit` test still passes;
the MCP server's tool catalog auto-grows when an OpenAPI operationId
is added.

### Phase 7 — Backfill the 253 missing endpoints as OpenAPI specs (6-10 weeks)

The matrix CSV from PR #41 enumerates the 253 missing endpoints
across 10 collections. Author `contracts/openapi/{pm,options,
pm-pro,crypto-loan,convert-sapi,algo-sapi,dual-investment,alpha,
copy-trading,c2c}.yaml` for each. Because Phases 2-6 already wired
the codegen pipeline, **no TypeScript needs to be hand-written**
to land these endpoints — the generators emit everything.

**Exit criterion**: the matrix CSV's `Status` column is 100 %
`Covered`; the audit's 253 missing-endpoint count drops to 0.

### Phase 8 — Lock-down CI (1 week)

Final guardrails so the contract cannot silently rot again:

- `grep -L "^// @generated" src/{resources,types,registry,ws}/*.ts src/{resources,types,registry,ws}/**/*.ts && exit 1`
  — every file that should be generated carries the header.
- `redocly lint contracts/openapi/*.yaml` — OpenAPI specs are valid.
- `asyncapi validate contracts/asyncapi/*.yaml` — AsyncAPI specs are valid.
- A new `test/contracts/snapshot.test.ts` that snapshots the
  generated files; PRs that touch OpenAPI must regenerate the
  snapshots or fail.
- A scheduled job (the existing audit-digest cron at 6 AM IST)
  that opens an issue when `binanceApiSnapshot` is > 30 days old.

**Exit criterion**: CI runs in < 60 s; any hand-edit to a
generated file fails the build; any OpenAPI drift from Binance's
published API surfaces an issue within 24 h.

## What stays hand-written forever

Even a fully contract-first SDK keeps some hand-written code:

- **Composition helpers** (`FuturesOps.sizePosition`,
  `ExecutionManager.placeOrder`, `RiskGateway`,
  `UserStreamDispatcher`) — these wrap multiple endpoints with
  ergonomics Binance doesn't expose.
- **Test assertions** — generated skeletons can hit the endpoint
  with sample inputs, but the expected-output assertions stay
  hand-curated.
- **Paper trading engine** — the simulator's fill model and
  accounting are SDK ergonomics, not protocol surface.
- **MCP server bootstrap** — the server's transport and lifecycle
  are not derivable from the Binance API spec.

The 80/20 rule: ~80 % of the SDK becomes generated; ~20 % stays
hand-curated as ergonomic composition on top of the generated
surface.

## Recommendation

Start with Phase 1 — authoring OpenAPI for the existing 133
endpoints — because:

1. It's the foundation every later phase depends on.
2. It immediately closes drift in both directions (OpenAPI without
   a registry row fails CI; registry row without an OpenAPI
   operationId fails CI).
3. It needs no new tooling — just OpenAPI YAML and a CI test.
4. The audit matrix (PR #41) already enumerates every endpoint with
   proposed method names; that CSV is the to-do list for the OpenAPI
   authoring work.

Phases 2-6 are mechanical once Phase 1 lands. Phase 7 is the long
tail that benefits most from having the codegen pipeline already
in place.

After Phase 1, the answer to *"is the SDK contract-first?"* changes
from "no, it's registry-first" to "yes, the inventory layer is
OpenAPI-driven; the schema/method layer is still being migrated".
After Phase 4, the answer is "yes, fully".
