# v3 Architecture — WebSocket Platform (Milestone 2)

Status: implemented in `3.0.0-next.2` · branch `sdk-v3-websocket`

## The problem

v2's WebSocket surface was capable but connection-centric. Every product
namespace built its own sockets (`client.futures.ws`, `client.spot.ws`, …),
callers juggled raw EventEmitter APIs and stream-name strings, the WS API
opened a *socket per request*, and liveness/renewal timing was invisible.

## The platform

`src/ws/platform/` turns that plumbing into one closure-shared runtime,
exposed lazily as `client.ws` (via `CoreContext.ws`, so the facade and every
standalone product client share the same pools):

```
WsPlatform
├── usdm / spot / coinm   WsFamilyStreams ── subscribe() → Subscription objects
│     └── FamilySubscriptionRegistry  (refcounts, fan-out, reconnect repair)
│           └── FamilyConnectionPool  (capacity packing: 200/1024 streams per conn)
│                 └── WsConnection    (existing v2.1 state machine, unchanged)
├── api.usdm / api.spot   persistent multiplexed WS API clients
├── WsHeartbeat           one timer for all connections (10-min stale cut-off)
└── RenewalController     staggered 23h renewals, concurrency-capped
```

## Consumer API

```ts
const client = new BinanceClient({ apiKey, apiSecret });

// Subscriptions are objects, not stream-name bookkeeping.
const sub = await client.ws.usdm.subscribe('btcusdt@aggTrade');
sub.on('message', (tick) => console.log(tick.p));   // parsed + lossless raw
sub.on('state', (s) => …);                          // pending → live → …
await sub.waitForReady();
sub.close();                                        // refcounted UNSUBSCRIBE

// Batches spread across pooled connections automatically.
const books = await client.ws.usdm.subscribe(
  Array.from({ length: 450 }, (_, i) => `sym${i}@depth20`),  // → 3 connections
);

// WS API: REST-style promises over ONE persistent socket.
await client.ws.api.usdm.accountStatus();
const [a, b] = await Promise.all([                  // multiplexed by id
  client.ws.api.usdm.ticker24hr({ symbol: 'BTCUSDT' }),
  client.ws.api.usdm.time(),
]);

// Observability.
client.ws.stats();   // per-connection state, streams, renewal deadlines
```

## Semantics

| Concern | Behavior |
|---|---|
| Confirmation | `subscribe()` resolves only after the server acks; `Subscription.state` is `pending` → `live` |
| Fan-out | N subscriptions to one stream share one server-side stream; last close issues UNSUBSCRIBE |
| Reconnects | Connection-level repair (v2.1 resync) re-confirms; subscriptions cycle `pending → live` |
| Pooling | Least-loaded packing against documented ceilings (usdm 200, spot 1024, coinm 200 streams/connection) |
| Liveness | One heartbeat timer platform-wide; 10 min of total silence (pings count) → terminate-and-reconnect |
| Renewal | 23h zero-gap rotation (1h before Binance's 24h kill), ±10 min jitter, max 1 concurrent platform-wide |
| WS API | One persistent socket; in-flight requests fail as retryable `NetworkError` on drop; auto-reconnect with jittered backoff |
| Backoff | Jittered exponential by default; pluggable (`exponentialBackoff` / `fixedBackoff` / `linearBackoff`) |

## Contract layer

`contracts/websocket-catalog.json` (generated by `npm run contracts:generate`,
CI-validated for drift by `test/contracts/catalog.test.ts`) records per-family
endpoints (live/testnet/demo), stream ceilings, connection lifetimes, and the
renewal/liveness policy — the input for generated bindings, tool metadata and
coverage accounting in later milestones.

## Backward compatibility

All v2 WS classes (`FuturesMarketWS`, `SpotUserWS`, `WsApi`, …) are untouched
and remain the canonical surfaces on product namespaces (`client.futures.ws`).
The platform is additive: `client.ws` constructs lazily, `closeAllWebSockets()`
closes it only when built, and no existing test changed.
